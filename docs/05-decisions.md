# 05 · 关键决策（ADR）

每条决策记录：背景、决定、理由、后果。后续推翻时新增一条，不改旧条。

---

## ADR-001 · 本地 ASR，云端 LLM

**背景**：隐私、延迟、成本三者要平衡。

**决定**：ASR / VAD / TTS 在本机跑；LLM 走云端 API（默认 DeepSeek）。

**理由**：
- ASR 实测 RTF 0.025，本地几乎免费，且音频不出机器；
- 本地 4B 模型的中文对话质量明显不如云端；
- 首 token 延迟差距只有约 200 ms，不值得为它牺牲质量。

**后果**：断网时对话不可用。M4 再评估本地 4B 兜底，
但即使做，也只作为"离线模式"而非默认路径。

---

## ADR-002 · Rust 核心 + WebView 渲染

**背景**：实时音频要求高，3D 资产与 UI 迭代要求快。

**决定**：音频、推理、编排用 Rust；界面与数字人用 TypeScript + Three.js。

**理由**：
- 音频回调是硬实时，GC/JIT 都不合适；
- glTF / morph target / 动画的工具链在 Web 侧最成熟；
- 单一 `.app` 分发，不依赖 Python 环境。

**后果**：两种语言、两套构建；IPC 协议必须先定义好。
若 Rust 阻塞进度，允许 TypeScript spike，但接口不变。

---

## ADR-003 · 先半双工，后全双工

**背景**：打断（barge-in）是整条链路最难的部分，涉及 AEC、回声参考、状态机。

**决定**：M1 只做"按住说话"；M2 再做 VAD 常开与打断。

**理由**：先把识别→回答→播放跑通，把回声问题隔离到后面。

**后果**：早期体验像对讲机。对外演示时要说明这是阶段性限制。

---

## ADR-004 · TTS 先轻后重

**背景**：CosyVoice 音色好，但没有 Rust 绑定、吃 GPU、启动慢；
Piper 音色一般，但 CPU 实时、依赖简单。

**决定**：M1 用 Piper（或 Kokoro）；M3 之后再评估 CosyVoice sidecar 或云 TTS。

**理由**：先保证延迟与稳定性，音色是最后一步。

**后果**：早期音色平庸。所以 TTS 接口从一开始就按
"流式 + viseme 时间轴"设计，换引擎不改上层。

---

## ADR-005 · 数字人走参数化 3D，不做实时视频生成

**背景**：写实视频数字人（LivePortrait / MuseTalk 类）在 M1 Max 上只有 8–15 fps，
且与 TTS 抢 GPU。

**决定**：glTF + blendshape + Three.js，参数驱动，不逐帧生成。

**理由**：
- 任意文本都能实时驱动；
- 720p 30 fps 在 M1 Max 上可行；
- 资产是一次性成本，运行时不烧 GPU。

**后果**：写实度有限，靠资产质量与光照；不追求照片级。
若未来要做写实，放到云端 GPU，不占本机。

---

## ADR-006 · 不用端到端语音模型（S2S）

**背景**：Realtime / Moshi / Qwen-Omni 类模型延迟低、语气自然。

**决定**：坚持 ASR → LLM → TTS 的文本管线。

**理由**：
- 需要文本做日志、检索、工具调用；
- 数字人口型需要文本与时间戳，S2S 给不了；
- 可控性高，便于调试与替换单点。

**后果**：延迟略高，用流水线重叠弥补；
语气自然度不如 S2S，靠 TTS 的音色与韵律补。

---

## ADR-007 · 不把 Python 作为必需依赖

**背景**：Python 生态有现成的语音框架与 TTS 实现。

**决定**：Python 只能以 sidecar 形式存在，且功能可降级。

**理由**：安装包体积、启动时间、跨平台分发都会被 Python 拖累。

**后果**：CosyVoice 这类只有 Python 的模型，要么等 ONNX 版本，
要么接受 sidecar 的额外复杂度。
