# 05 · 关键决策（ADR）

每条决策记录：背景、决定、理由、后果。后续推翻时新增一条，不改旧条。

---

## ADR-001 · 本地 ASR，云端 LLM

**背景**：隐私、延迟、成本三者要平衡。

**决定**：ASR / VAD / TTS 在本机跑；LLM 走云端 API（默认 DeepSeek）。

**理由**：
- ASR 实测 RTF 0.025，本地几乎免费，且音频不出机器；
- 本地 4B 模型的中文对话质量明显不如云端；
- 首 token 延迟差距只有约 200 ms，不值得为它牺牲质量。

**后果**：断网时对话不可用。M4 再评估本地 4B 兜底，
但即使做，也只作为"离线模式"而非默认路径。

---

## ADR-002 · Rust 核心 + WebView 渲染

**背景**：实时音频要求高，3D 资产与 UI 迭代要求快。

**决定**：音频、推理、编排用 Rust；界面与数字人用 TypeScript + Three.js。

**理由**：
- 音频回调是硬实时，GC/JIT 都不合适；
- glTF / morph target / 动画的工具链在 Web 侧最成熟；
- 单一 `.app` 分发，不依赖 Python 环境。

**后果**：两种语言、两套构建；IPC 协议必须先定义好。
若 Rust 阻塞进度，允许 TypeScript spike，但接口不变。

---

## ADR-003 · 先半双工，后全双工

**背景**：打断（barge-in）是整条链路最难的部分，涉及 AEC、回声参考、状态机。

**决定**：M1 只做"按住说话"；M2 再做 VAD 常开与打断。

**理由**：先把识别→回答→播放跑通，把回声问题隔离到后面。

**后果**：早期体验像对讲机。对外演示时要说明这是阶段性限制。

---

## ADR-004 · TTS 先轻后重

**背景**：CosyVoice 音色好，但没有 Rust 绑定、吃 GPU、启动慢；
Piper 音色一般，但 CPU 实时、依赖简单。

**决定**：M1 用 Piper（或 Kokoro）；M3 之后再评估 CosyVoice sidecar 或云 TTS。

**理由**：先保证延迟与稳定性，音色是最后一步。

**后果**：早期音色平庸。所以 TTS 接口从一开始就按
"流式 + viseme 时间轴"设计，换引擎不改上层。

---

## ADR-005 · 数字人走参数化 3D，不做实时视频生成

**背景**：写实视频数字人（LivePortrait / MuseTalk 类）在 M1 Max 上只有 8–15 fps，
且与 TTS 抢 GPU。

**决定**：glTF + blendshape + Three.js，参数驱动，不逐帧生成。

**理由**：
- 任意文本都能实时驱动；
- 720p 30 fps 在 M1 Max 上可行；
- 资产是一次性成本，运行时不烧 GPU。

**后果**：写实度有限，靠资产质量与光照；不追求照片级。
若未来要做写实，放到云端 GPU，不占本机。

---

## ADR-006 · 不用端到端语音模型（S2S）

**背景**：Realtime / Moshi / Qwen-Omni 类模型延迟低、语气自然。

**决定**：坚持 ASR → LLM → TTS 的文本管线。

**理由**：
- 需要文本做日志、检索、工具调用；
- 数字人口型需要文本与时间戳，S2S 给不了；
- 可控性高，便于调试与替换单点。

**后果**：延迟略高，用流水线重叠弥补；
语气自然度不如 S2S，靠 TTS 的音色与韵律补。

---

## ADR-007 · 不把 Python 作为必需依赖

**背景**：Python 生态有现成的语音框架与 TTS 实现。

**决定**：Python 只能以 sidecar 形式存在，且功能可降级。

**理由**：安装包体积、启动时间、跨平台分发都会被 Python 拖累。

**后果**：CosyVoice 这类只有 Python 的模型，要么等 ONNX 版本，
要么接受 sidecar 的额外复杂度。

---

## ADR-008 · 数字人是"角色"，不是用户分身

**背景**：最初把产品定义为"你自己的数字分身"（twin），隐含三件事：声音克隆、
形象复刻、个人记忆。三样都会把 M1–M3 的排期翻倍，且与"闲聊陪伴"的核心体验无关；
声纹与面部数据还是敏感数据，会连带隐私与许可问题。

**决定**：产品定位改为**角色化对话**。预设 3 个角色（不同的声音、性格、说话方式），
用户选择其一进行互动；不做用户本人的声音/形象克隆。"记忆"只做角色内的对话连续性，
不做个人化建模。

**理由**：
- 角色的声音、形象、人设可以一次性制作，不依赖用户提供素材；
- 3 个预设角色天然形成对照：同一套管线换人设与音色，就能测"角色感"是否成立；
- 绕开声纹/人脸的隐私与授权问题。

**后果**：
- 名字 GabTwin 保留，但 twin 不再指"用户的复制品"；对外文案要改成"和一个角色聊天"。
- TTS 从"克隆"回到"多音色"：每个角色一个音色。音色质量、许可、切换成本都要在选型时评估。
- 角色资产（声音、形象、人设文本）成为一条独立的内容工作流。链路验证阶段先 1 个角色，
  3 个角色在语音与 TTS 验证通过后补齐。
- 若以后要做"分身"，应当是新的产品线，不塞回本项目。

## ADR-009 · 模型下载：国内镜像、禁代理直连、并行校验

**背景**：模型首次启动要下 167 MB（ASR），后续还有 TTS 音色与 VAD。实测本机
`huggingface.co` 直连超时，`hf-mirror.com` 直连 200；而系统里常驻 Clash 代理
（127.0.0.1:7890），下载走代理会多一个失败点，且同样可能被限流。

**决定**：

1. 默认镜像 `https://hf-mirror.com`，可用 `GABTWIN_HF_MIRROR` 覆盖；
2. **强制直连**：脚本先清空 `http_proxy/https_proxy/all_proxy`，curl 再加 `--noproxy '*'`；
3. **并行下载**（默认 4 路），每个文件独立重试、断点续传、429/5xx 退避；
4. 每个文件下载后校验 sha256，不匹配就删掉重下，绝不把坏文件留给识别器；
5. 应用内下载器（M4）实现同一套规则，不另起一套。

**理由**：
- 国内镜像在本地实测可用，且不需要代理；
- 并行下载把"四个文件串行"压成"最慢那个文件"的时长；
- 哈希固定后，镜像内容滞后或投毒都会当场失败，而不是变成难查的识别异常。

**后果**：
- 海外用户或私有镜像需要改 `GABTWIN_HF_MIRROR`；
- 镜像不可用时没有默认回退，脚本直接报错（比悄悄退回慢速直连更好排查）；
- 模型清单（文件名 + sha256）随代码走，见 `scripts/fetch-model.sh`。

## ADR-010 · 默认 ASR 改为中英九语流式模型

**背景**：中文专用模型（zipformer zh 2025-06-30）中文几乎完美，但把英文按中文谐音转写
（"Can you hear me now" → "看你有些没拿"）。产品是中文闲聊、偶尔夹英文，不能只会中文。

**决定**：默认模型改为 `streaming-zipformer-ar_en_id_ja_ru_th_vi_zh-2025-02-10`
（9 语含中英，chunk 16）；纯中文模型保留为可选；中英双语 2023 模型（Apache-2.0）只作对照。

**理由**（同一套 26 句评测，见 [dev/02](dev/02-asr-model-compare.md)）：

| 模型 | 英文 | 中文 | RTF |
|---|---|---|---|
| 中文专用 | 115% | 0.0% | 0.082 |
| 中英双语 2023（Apache-2.0） | 2.2% | 6.2%（重复字） | 0.055 |
| **九语 2025（采用）** | **0.0%** | **1.4%** | 0.102 |

**后果**：
- 英文可用；中文从 0% 退到 1.4%，是明确的取舍；
- 模型 340 MB、峰值内存 873 MB（比纯中文多约 340 MB），首字约 350–520 ms；
- **权重许可未标**（PengChengStarling），商用前必须确认；Apache-2.0 的双语模型可作为替代预案；
- 中英混说内的英文词仍弱，需要 hotwords/词表（下一步）。

## ADR-011 · 默认 ASR 定为中英 paraformer（撤回 ADR-010）

**背景**：ADR-010 把默认切到九语 zipformer。实测暴露两个问题：中文口音的英文会被它串成
日语/越南语（`你は`、`en như`）；用户真实会话里还遇到识别流卡死（端点门控，已单独修复）。

**决定**：默认改为 `streaming-paraformer-bilingual-zh-en`（FunASR，Apache-2.0，中英）。
九语模型退出默认，只作对照；纯中文与中英 zipformer 保留为可切换项。

**理由**（同一套 26 句评测，预热量 0，见 [dev/02](dev/02-asr-model-compare.md)）：

| 模型 | 英文 | 中英混 | 中文 | 首字 | RTF | 许可 |
|---|---|---|---|---|---|---|
| paraformer（采用） | 10.9% | 25.5% | **0.7%** | 550 ms | 0.185 | Apache-2.0 |
| 中英 zipformer | 2.2% | 39.2% | 6.2% | 385 ms | 0.055 | Apache-2.0 |
| 九语 zipformer | 0.0%* | 27.5% | 1.4% | 519 ms | 0.106 | 待核 |

\* 干净美音 TTS；中文口音英文会串语种。

**后果**：
- 中文与混说是四个模型里最好的，且不会串语种；
- **英文会漏词**（10.9%），英文优先时切 `streaming-zipformer-bilingual-zh-en-2023-02-20`；
- paraformer 首字略慢（550 ms）、RTF 0.185，仍在预算内；内存 530 MB；
- 许可干净（Apache-2.0），比九语模型更适合商用路径。

## ADR-012 · 流式出字 + SenseVoice 句末定稿

**背景**：单一模型无法同时满足"实时出字"和"中英都准"：paraformer 英文漏词、罕见词错；
SenseVoice 几乎全对且带标点，但它是离线模型。

**决定**：流式 paraformer 负责 partial；每句话结束时用 SenseVoice 重解这段音频，
替换句末文本。`GABTWIN_ENGINE=streaming` 可退回纯流式。

**理由**（实测见 [dev/02](dev/02-asr-model-compare.md)）：
- 中文："狸花猫"从错到对；英文整句从"schedule a"到完整带标点；
- 只改会话层的一小段，不动流式、端点与 UI；
- 定稿延迟 0.66–1.31 s，仍在 M1 的 1.5 s 首响预算内。

**后果**：
- 句末多 200–400 ms；内存 905 MB（两个模型）；
- partial 无标点，定稿才有；
- SenseVoice 权重许可（FunASR 自定义）商用前必须确认；
- 若以后要单模型，再评估全 SenseVoice 滑窗方案。

## ADR-013 · LLM 接话：句末触发、流式、可取消

**背景**：识别已经能出带标点的定稿。需要一个"说完就接话"的回路，且首 token 要快，
不能让用户对着转圈等。

**决定**：
1. **句末定稿后触发**，不用 partial（partial 会改，回复会对不上）；
2. **SSE 流式**，来一个字显示一个字；
3. **新语音取消上一轮**：turn_id + 取消旗标，旧 delta 到 UI 被丢弃；
4. 上下文 = system + 最近 12 条 / 4000 字，system prompt 强制口语化短句；
5. key 从 `DEEPSEEK_API_KEY`（或 `GABTWIN_LLM_KEY`）读，没有就只显示识别结果。

**理由**：首 token 是体验的核心；流式把"等全文"变成"边说边出"。
上下文预算保证长对话下首 token 不退化。取消保证新语音永远优先。

**后果**：
- 首 token 预算约 0.5–1.0 s（定稿 0.2–0.4 s + 网络 0.3–0.6 s），待真 key 实测；
- 对话不持久化，重启即清零；
- 单人设；3 个角色等 TTS 音色一起做；
- 未做重试/限流/内容过滤，属于自用阶段的已知缺口。

## ADR-014 · TTS 用本机 VITS，句级流式，播放时半双工

**背景**：LLM 已经能流式回字。要让它"说出来"，且首句不能等全文；同时 M1 还没有 AEC。

**决定**：
1. 本机 sherpa-onnx VITS（16 kHz，`vits-zh-ll`），不走云 TTS；
2. 按句合成：首句 ≤6 字，之后按标点/30 字切；碎片攒到下一句；
3. 合成与播放分离：TTS worker 合成 → 重采样到 48 kHz → cpal 队列播放；
4. **播放期间屏蔽麦克风**（半双工），播完 +250 ms 恢复。

**理由**：
- 本机合成延迟可控、音频不出机器；
- 首句 6 字把"句末 → 出声"压到约 0.6 s（不含 LLM）；
- 没有 AEC 时，不屏蔽麦克风必然自问自答，这是必须付的代价。

**后果**：
- 说话时不能插话，只能点停止（M2 用 AEC + 双阈值解决）；
- 中文 lexicon 跳过英文/生词；
- 单音色；3 个角色的音色要另做；
- VITS 权重许可待核，商用前必须确认。
