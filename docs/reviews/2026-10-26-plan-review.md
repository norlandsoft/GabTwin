# 规划评审 · GabTwin M0

- 评审对象：`README.md` 与 `docs/00`–`06`（commit `2347c98`）
- 评审日期：2026-10-26
- 评审人：AI 评审（DeepSeek Harness），事实性结论均标注了来源
- 结论：**架构方向可以保留，但先别写代码**。有 5 个决定、3 处协议、2 处指标口径需要先改；不改的话，M2 会返工音频层、M3 的口型验收做不到、M1 做完会得出"能聊但不好聊"。

---

## 一、总评

### 做得好的地方

1. **范围收得住**：非目标写得比目标还清楚（不接智能家居、不做会议转录、不做写实数字人），这在业余项目里是最稀缺的纪律。
2. **顺序对**：先半双工再全双工、数字人最后接、不并行开三条线。这三条判断把最容易失控的两件事（AEC、资产）都推到了后面。
3. **延迟预算是真的算过的**：三处重叠（ASR final→LLM、首句→TTS、首包→开播）是对的，也是唯一能让 1.5 s 成立的办法。
4. **对不确定性诚实**：许可写"待核"、模型写"未验证"、ADR 写"后果"，没有把假设伪装成结论。
5. **模型管理是生产级思路**：revision + sha256 + `.part` + 多源 HEAD 探测 + 不自动升级。这一块比很多商业项目做得细。

### 核心判断

这份文档是一份很好的**管线计划**，还不是一份**对话产品计划**。

它把"声音进 → 文字 → 回答 → 声音出"的每一段都算清楚了，却没有任何一条验收标准在问：*它接话接得自然吗？记得住五分钟前说过什么吗？像人还是像在朗读？* 对"陪伴闲聊"这个定位，这恰恰是决定成败的那一半。

另外有三处是"选错了就要重写一层"的，不是"晚几天"的：音频层的双工形态、TTS 的中文能力、口型的时间来源。这三处现在都写在 M1/M2/M3 里，但它们的决定其实必须在 M0 做完。

### 三个必须先回答的问题

| # | 问题 | 为什么现在答 | 不答的代价 |
|---|---|---|---|
| Q1 | 它是**你的分身**，还是**一个角色**？ | 决定要不要声音克隆、要不要形象复刻、隐私边界、甚至名字 | M1–M3 做出来的是"通用陪伴角色"，与"twin"的承诺不符 |
| Q2 | 音频层是**一路双工**还是**两路独立流**？ | VPIO 的 AEC 要求采集与播放挂在同一个 AudioUnit 上 | M2 接 AEC 时重写 `audio-in` / `audio-out` |
| Q3 | 口型的时间基准是**音频包络**还是**音素时间戳**？ | 本地 TTS 不给音素时长，"≤80 ms"没有来源 | M3 的验收指标无法测量、也无法达成 |

## 二、P0：写代码之前要定的五件事

### D1 · 身份：twin 还是 character

**现状**：`00-vision` 说"你自己的数字分身"，`README` 说 twin；但 03 的音色是通用 Piper 音色，形象是 VRM / Ready Player Me 占位，没有声音克隆、没有形象复刻。开放问题 #1 把这件事挂起了。

**问题**：这不是命名问题，是产品定义问题。真做 twin，需要三样现在没有的东西：你的声音（克隆）、你的脸（或至少你的风格）、你的记忆（人设与关系连续）。三样都是额外 2–6 周的量级，而且会推翻"TTS 先轻后重"的排期。

**建议**：M0 内二选一，写进 ADR。

- 选 **twin**：音色从"预设"改为"克隆"。好消息是不用等 CosyVoice sidecar——sherpa-onnx 已带 ZipVoice（中文/英文、int8、zero-shot 克隆，需参考音频 + 参考文本），仍在 Rust 进程内，不引入 Python。
- 选 **character**：把 `00-vision` 的"你自己的分身"改成"一个有性格的对话角色"，成功标准里删掉与"分身"绑定的表述。名字可以留，承诺要改。

### D2 · TTS 选型证据不足，而且默认选项踩了自己的许可红线

**现状**：ADR-004 定 Piper（或 Kokoro），03 的 M1 定 Piper。理由是"CPU 实时、依赖简单"。

**核实到的事实**：

- Piper 官方音色库里中文只有 3 个：`chaowen` / `huayan` / `xiao_ya`。
- `huayan` 的 MODEL_CARD 写明训练数据 HuaYan_TTS 的 **License: Unknown**，且是从英文 lessac 音色微调来的。
- 规划自己在 06 / R5 写："任何许可不明的资产，默认不用于商用版本。"
- 中文 G2P（分词、多音字、数字、英文缩写）在 Rust 侧最薄——文档自己承认了（02），但没有对应的工作项。piper-rs 的音素化走 `espeak-rs`（espeak-ng），中文韵律和多音字是它的弱项。

也就是说，M1 的默认 TTS 正好是"许可不明"的那一个。这条不解决，"商用前逐项确认"就会变成 M4 的一次硬阻塞。

**建议**：把 TTS 当成 M0 的决策性 spike，而不是既定事实。至少比较三个候选，用同一套 30 句中文测试集盲听：

1. **sherpa-onnx 自带 TTS**（推荐优先试）：`sherpa-onnx 2.0.0` 已在 crates.io，Rust API 里有 `OfflineTts`，支持 VITS / Matcha / Kokoro / Kitten / ZipVoice / Pocket，中文模型由同一项目维护。若采用，VAD + ASR + TTS 共用一个运行时，可以**去掉 piper-rs 和 ort 两个依赖**，中文前端也不用自己写。
2. **Kokoro-82M（含 v1.1-zh）**：Apache-2.0，音质好；但要确认中文前端质量与 RTF。
3. **Piper**：只有在许可能查清、且盲听可接受时才留。

评分项固定为：许可可商用 / 盲听 MOS / 首句合成耗时 / RTF / 是否支持克隆。**先测再写 ADR-004**。

> 注意：本地 TTS 是"整句合成"，不是流式。"TTS 首包 150–300 ms"这个说法要改成"首句合成完成"，并据此约束第一句的长度（≤10 字）。

### D3 · AEC 是全局最大风险，却被排成 M2 的 2 周任务；macOS 上还有更省事的选项

**现状**：01 的模块表把 AEC 放在 `audio-in`，02 选 `webrtc-audio-processing = "0.3"`，04 把 AEC 排在 M2。

**核实到的事实**：

- `webrtc-audio-processing` 现在最新是 **2.1.0**（文档写的 0.3 已很旧），而且默认构建是**动态链接**系统里由 PulseAudio 打包的库；macOS 上没有这个库，必须开 `bundled` 特性从 git submodule 编 C++。
- macOS 自带系统级回声消除：CoreAudio 的 VoiceProcessingIO 音频单元（AVAudioEngine 的 voice processing 就是它的封装，macOS 10.15+）。原生语音应用多数直接用这个，而不是自己接 APM。

**更关键的是架构约束**：走 VPIO 意味着采集与播放必须挂在**同一个双工 AudioUnit** 上；而 01 的图是"cpal 采集"+"播放缓冲"两路独立流。这两件事不兼容。也就是说，**音频层是不是双工，是 M0 的决定，不是 M2 的决定**——M2 才改，等于把 `audio-in` / `audio-out` 重写一遍。

**建议**：

1. M0 加一个 1 天的 AEC spike：内置扬声器 70% 音量播 TTS，分别试 VPIO 与 webrtc APM，量两件事——自打断次数、残余回声（粗测 ERLE 即可）。
2. `audio-in` 的抽象从一开始就允许"双工单元"，不要绑死 cpal。cpal 不暴露 VPIO。
3. M2 的 barge-in 还缺三块，现在没写：
   - **pre-roll 环形缓冲**（≥500 ms）：打断判定要 200 ms 才成立，那 200 ms 的音频必须已经在缓冲里，否则 ASR 丢掉用户开口的第一句。
   - **flush 淡出**（5–10 ms）：停播时直接清队列会有爆音。
   - **蓝牙耳麦策略**：AirPods 一旦开麦就切到 HFP（8/16 kHz 单声道），音质像打电话，而且 AEC 参考不可靠。建议 M2 验收明确"有线/内置扬声器"，蓝牙列为降级路径并给提示。

### D4 · 延迟口径自相矛盾，且没有留痕机制

**现状**：00 与 M1 把"首响"定义为"按住说话 → 扬声器出声"（不含端点）；01 的预算表里却有"端点 500–700 ms"。

**算术核对**（01 的表，单位 ms）：

- 逐项最小和 = 20+10+150+500+300+150+30 = **1160**
- 逐项最大和 = 40+30+300+700+600+300+60 = **2030**

表里写"合计 1.0–1.6 s"，与自己的逐项数据对不上。**按键说话**时去掉端点 500–700，得 0.66–1.33 s，M1 的 ≤1.5 s 成立；**M2 常开麦**时端点必须计入，串行就是 1.16–2.03 s，三处重叠省 300–600 ms 后仍在 0.56–1.73 s——p50 有可能达标，p90 一定不达标。

**建议**：

1. 定义唯一的时间口径：`t0` = 松键（M1）/ 端点确认（M2），`t1..t5` 为各阶段，事件带上 `turnId` 与时间戳。
2. **从 M1 第一天就写 trace**（`GABTWIN_TRACE=1` 输出 JSONL），否则你只能知道"慢了"，不知道慢在哪一段。这条应该进 M1 的完成定义。
3. 指标从中位数改成 **p50 + p90**：p50 ≤1.2 s、p90 ≤1.8 s（M1）；M2 另立目标，不要让 M1 的数字悄悄继承过去。

### D5 · 对话契约缺位：人设、上下文、首启

**现状**：`dialog` 模块只写了"状态机、上下文、超时、取消"；`set_persona` 命令没有 schema；M4 才有设置页；"记忆"是开放问题。

**问题**：

- M1 没有设置页就跑不起来（要填 API Key、要下载 240 MB 模型、要选设备）。把首启流程放到 M4 是排期错误。
- 上下文没有预算：多少轮、超限怎么办、要不要摘要。闲聊 10 分钟就会撞上。
- 没有"口语化"约束：LLM 默认会输出 markdown、列表、emoji、括号旁白，TTS 会照读。这是"像不像人"的第一道坎，却没有任何一处规定。

**建议**（都可以在 M1 之前用文档定下来）：

1. 人设文件格式（Markdown + front matter）：名字、语气、禁用词、说话长度上限。
2. 口语化系统提示契约：短句、无 markdown、无 emoji、不用列表、首句 ≤10 字、一次最多 2–3 句。
3. 上下文策略：保留最近 N 轮 + 滚动摘要；人设放在最前面保持前缀稳定（云厂商若支持前缀缓存，这直接省首 token 与费用）。
4. 转写是否落盘：默认关；开了就 0600 + 保留期 + 日志脱敏。音频不出本机是真的，但**文本会出去**（LLM，若用云 TTS 则还有 TTS），这一点要在 README 写清楚，别写成"什么都不出本机"。

## 三、P1：协议与架构问题（现在改便宜，M2 改很贵）

### A1 · `turnId` 缺失：打断之后，旧回复还会继续到达

事件表里没有回合标识。barge-in 时取消 LLM 与 TTS，但网络上已经在飞的 SSE delta 和已合成的音频包还会到达——没有 `turnId`，UI 与播放层无法判断"这是上一轮的"，典型表现是打断后又说半句、字幕闪回。

**建议**：所有事件带 `turnId`（单调递增）；取消 = 递增 + 丢弃旧 id；Rust 与 UI 两端都做丢弃。

### A2 · 把 PCM 塞进 Tauri IPC，且没有播放时钟

`tts.chunk` 带 `pcm` 与 `visemes[]`。两处问题：

1. **不该过 IPC**：16 kHz f32 单声道 = 64 KB/s，JSON 数字数组会膨胀 5–10 倍，50 次/秒。若播放本来就在 Rust，UI 收 PCM 没有意义（它也不能更准地播）。Tauri 2 有原始字节通道（`tauri::ipc::Response`），真要传就走它；更好的做法是音频完全不过 IPC。
2. **`tMs` 相对音频包起点**：这是"到达时间"，不是"出声时间"。一旦有缓冲、抖动或换设备，口型立刻漂移。

**建议**：播放层是唯一权威。UI 只收 `avatar.frame { audioClockMs, visemes[], emotion }`，以"已写入设备的帧数"为时钟，30–60 Hz 推；口型永远跟 audible 位置，不跟到达时间。同时明确：喂给 AEC 的参考必须是**送去 DAC 的那份样本**，不是重采样前的缓冲。

### A3 · 口型验收（≤80 ms）与选定方法不匹配

**现状**：03 的 M3 用"拼音声母/韵母 → 12 类 viseme"驱动，验收要求口型偏差 ≤80 ms。

**问题**：本地 TTS 输出的是音频，不输出音素与时长。文本推口型只能得到"顺序"，得不到"时间"；没有对齐就没有 80 ms 这个量级。而且"口型偏差"怎么量，文档没定义。

**建议**（按成本从低到高）：

1. **包络 + 文本混合**（推荐）：张嘴幅度取播放音频的短时能量包络（本来就有时钟），口型形状取文本 viseme。稳、便宜、不需要时间戳；验收放宽到 ≤120 ms，并写清测量方法（录屏 + 录音，标 viseme 起始与音频起始）。
2. 换一个能给出对齐信息的 TTS（云 TTS 的 viseme 时间戳；少数 ONNX 模型带时长）。
3. 用 ASR 强制对齐反推时长：能跑，但多一条链路、多一份延迟，不建议。

### A4 · 状态机缺态，且"常开麦"没有产品决策

缺：`error`（但事件表里有 `error`）、`warming`（模型加载 581 ms + TTS 预热）、`muted`。M2 常开麦意味着麦克风一直开着——macOS 的橙点常亮、耗电、观感像在窃听。对"陪伴"产品，这是要明说的产品决策。

**建议**：默认按住说话，常开麦是显式开关；加静音热键；每个状态写清超时与退出条件。

### A5 · `asr.partial` 在协议里，但不在关键路径上

M1 用整段 SenseVoice，M2 的流式 zipformer 是"未验证"。但仔细看：**回复回路只需要端点后的 final**，partial 只服务于实时字幕。也就是说 M2 的排期不依赖流式 ASR——这其实是好消息，但文档写反了：它把"流式/整段"并列成 `asr` 的职责，又列了 `stablePrefix`，容易被读成"必须有流式模型"。

**建议**：明确 partial 是可选的字幕增强；M2 的真实依赖是端点判定 + AEC + barge-in 状态机 + pre-roll，把这四项列成 M2 的四个子项。

### A6 · 依赖清单与版本策略自相矛盾

- 文档说"版本号锁定，不追新"，但 `sherpa-onnx = { git = ..., branch = "master" }`——master 是移动靶，且与"可复现构建"直接冲突。crates.io 上已有官方 `sherpa-onnx 2.0.0`（2026-10-23），没有理由跟 git。
- 清单版本已过时：cpal 0.15 → 0.18.2；rubato 0.16 → 5.0.1；webrtc-audio-processing 0.3 → 2.1.0；`ort` 仍是 `2.0.0-rc.x`（不是稳定版）。若采用 sherpa-onnx 的 TTS + VAD，`ort` 可以整个去掉，少一个 ONNX 运行时。
- `sherpa-onnx` 的 Rust crate 在构建时默认**下载预编译原生库**——离线构建、供应链审计、CI 缓存都要提前想清楚（可用 `SHERPA_ONNX_LIB_DIR` / `SHERPA_ONNX_ARCHIVE_DIR` 固定）。
- 应用（不是库）必须提交 `Cargo.lock`。

### A7 · 采样率要分入/出两条，不是一个"内部 16 kHz"

01 写"内部音频：20 ms 帧、f32、16 kHz"，但 TTS 输出通常是 22.05/24 kHz，设备播放是 48 kHz，AEC 必须在设备采样率上跑。把"内部音频"统一成 16 kHz 会让播放质量与 AEC 参考都被低估。另外"VAD 每 10 ms"+"20 ms 帧"+"Silero 512 样本窗"（16 kHz 下 = 32 ms）是三个互相打架的粒度。

**建议**：写明"采集链路 48 kHz → AEC/NS（48 kHz）→ 16 kHz 给 VAD/ASR"；"播放链路 TTS 原采样率 → 48 kHz → DAC，参考取 48 kHz 最终样本"；帧长统一 20 ms，VAD 用 512 样本窗，判定延迟 = 32 ms 窗 + hangover。

### A8 · 模块所有权有空洞

`llm` 明确"不负责句子切分"，`tts` 是"文本→音频"，`dialog` 只列了状态机/上下文/超时/取消——**没有人负责分句与文本规范化**（数字、英文、URL、emoji、括号旁白）。这正是"听起来像念稿"的常见来源。

**建议**：新增 `text` 模块（或明确归 `dialog`）：流式分句（中文标点、跨 chunk、英文缩写）、TTS 前清洗、emoji→表情映射、数字/单位读法。给它单独的单测。

> **如果只改三处**，就改这三处（每处都不超过半天，但都是 M2 返工的开关）：
> 1. 所有事件加 `turnId`，取消即递增，两端丢弃旧回合；
> 2. 口型与字幕以播放时钟为基准（事件带 `audioClockMs`），不以包到达时间为基准；
> 3. 音频层按"一路双工"抽象（VPIO 与 cpal 都只是它的实现），先不锁定。

## 四、P1：指标与验证方法

| 指标 | 现在的问题 | 建议 |
|---|---|---|
| 首响 | 中位数掩盖长尾；口径混用（端点算不算） | p50 ≤1.2 s、p90 ≤1.8 s；固定 t0；每阶段单独记 |
| 字错率 ≤5% | 自建 50 句、安静环境、朗读语料 = 对着 demo 过拟合；没定义归一化规则（标点/数字/繁简） | 两套集：朗读 50 句（≤5%）、自由说/远场 50 句（≤12%）；先定归一化规则；报 n 与置信区间；加一条噪声条件 |
| 连续 10 轮不崩 | 10 轮是演示，不是稳定性 | 30 分钟 soak：无崩溃、RSS 无单调增长（首末差 ≤100 MB）、设备热插拔各 1 次；R9 写成"低可能"不成立 |
| 自打断 ≤1/20 | "正常音量"未定义；只测了误触发，没测漏触发 | 写清设备/距离/音量/测试素材（音乐、播客、TTS）；同时测"真打断是否 100% 停下" |
| GPU ≤50% | WebView 里怎么量没写 | 用 Metal System Trace 或 `powermetrics`，写进验收步骤 |
| 离线可用 | 若默认云 TTS，则"断网仍能合成"不成立 | 云 TTS 必须 opt-in；离线模式只走本地，并把"哪些文本会出网"列表化 |

## 七、建议的 M0'（5 天，4 个决策性 spike）

只做能改变决策的四件，每件 1 天，第 5 天写结论。其余验证并入 M1 第一周。

| # | Spike | 做法 | 通过阈值 | 不通过则 |
|---|---|---|---|---|
| S1 | AEC 路线 | 内置扬声器 70% 音量播 TTS 10 分钟，VPIO vs webrtc APM 各测一遍 | 自打断 0 次；ERLE ≥20 dB（粗测）；耳机下 barge-in 100% 触发 | 接受"仅耳机可打断"，写进 M2 验收并降级外放体验 |
| S2 | 中文 TTS | 3 候选 × 30 句固定集，盲听 + 计时 + 查许可 | MOS ≥3.5/5；首句（≤10 字）≤300 ms；RTF ≤0.3（2 线程 CPU）；许可可商用 | 换候选；仍不行则 M1 接受"音色一般"，但把云 TTS 提前到 M2 |
| S3 | 渲染与口型 | 720p 30 fps + 包络驱动张嘴，量 GPU 与口型偏差 | GPU ≤50%；口型偏差 ≤120 ms（测量方法先写死） | 降分辨率/降帧；口型退化为"说话时张嘴 + 停顿闭嘴" |
| S4 | 对话体感 | TS walking skeleton（sherpa-onnx-node）：按键→ASR→LLM→TTS→播放，10 段脚本对话 | 首响 p50 ≤1.5 s；主观 ≥3.5/5（自然度/接话/人设一致）；"愿不愿意明天再用一次"= 是 | 先改对话契约（D5）再谈 Rust |

S4 单独说明：02 里已经写了"允许 TS/Electron spike"，但把它定位成"Rust 阻塞时的退路"。建议反过来——**先用 5 天把"好不好聊"验掉，再决定要不要投入 2–3 个月做 Rust**。事件协议已经定义好了，移植是机械工作；而"聊起来是否舒服"是存亡问题，越早知道越好。

**M0' 退出条件**：Q1–Q3 有答案；ADR-004 重写；依赖清单锁定版本；一份 200 字以内的"我们能承诺什么"写进 README，替换现在的"状态：M0 规划阶段"。
